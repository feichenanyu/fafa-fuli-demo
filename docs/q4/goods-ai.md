# 商品库可被 AI 调用：任务拆解与可行性

2026-11-03 · @sanyuan

「可被 AI 调用」拆成 5 层、共 22 项任务。其中 9 项可以在 11/20 前完成，足够支撑「商城选品」这种用结构化条件筛选的 AI 选品；语义检索、AI 打标、跨源同款和 MCP 封装放在 12 月及以后。工时是产品初估，待云程、侯局评估。

## 一、范围与边界

- **商家侧 / 供应商侧由阿胜主导规划**，包括商家定价权和抽佣。本文只列出买家侧和卖家侧必须对齐的交互点（见第四节）。
- **平台只管两类规则**：
  - 选品规则：商品池准入条件与自动上下架，AI 选品和商品池用同一套条件；
  - 平台运营规则：搜索排序与推荐权重、场景货盘、商城上线备注、站点巡检。
- 平台不定价：选品规则只读取价格结果做筛选（利润率、价格段），不参与定价。

## 二、「可被 AI 调用」的验收标准

AI 通过工具接口能完成五件事，每件事都有可检查的标准：

| 能力 | 验收标准 |
| --- | --- |
| 查：按条件找商品 | 品类、价格段、利润率、库存地区、来源、标签都能组合筛选，结果与商品池规则一致 |
| 读懂：理解商品 | 进入 AI 商品池的商品，必填字段完整率 100%，场景标签覆盖率达到约定值 |
| 判断：能不能卖、能不能发 | 库存状态、上下架、发货仓、可配送地区按约定频率同步 |
| 比：价格与同款 | 同一商品跨来源可识别，能给出参考价（12 月起） |
| 动：加购、询价、上架、下单 | 以工具形式开放，按角色过滤价格字段：会员侧不出接口价，平台利润率只给运营 |

## 三、任务拆解

现状基线：猫超约 54.6 万 SKU、优品约 3.3 万 SKU，另有京东及其他权益资源、自有商品和入驻商家商品。已知问题：

- 一级类目约 60 个且有重复，另有一套 8 个的场景类目；
- 库存多数只有状态，效期只有部分商品有；
- 发货仓只区分电商仓和商家仓；
- 京东接口文档停在 25 年 4 月；
- 10/31 会上对统一商品库的估算是 2 人 × 1.5 个月，聚合层方案在压测。

## 四、买卖家必须对齐的交互点

| 交互点 | 买家侧提供或需要 | 卖家侧提供或需要 |
| --- | --- | --- |
| 商品标准 | 提出 AI 选品、搜索要用的字段 | 上品表单和校验按同一标准 |
| 价格 | 选品规则只读价格做筛选 | 定价规则、佣金、价格竞争机制 |
| 行为数据 | 埋点采集曝光、浏览、关注、成交，并按商品、场景、价格段汇总 | 在商家后台展示，支持商家调价和选品 |
| 项目画像 | 商城上线备注、单位类型、预算段（脱敏） | 接收「商品已入选某类项目」的通知 |
| 推荐权重 | 排序规则里留出「平台核心供给」权重位 | 哪些商家或商品享受权重、换取什么条件 |
| 下单与履约 | 会员端下单、询价、报价单 | 订单下推、回单、物流回传 |

## 五、会上商家侧内容需要买家侧支持的事项

会上讲的商家侧内容，大多要靠买家侧先把数据和入口供上。最关键的是三件事：

1. **行为埋点 + 订单来源归因**：没有它，商家看不到曝光，平台也分不清「平台带来的单」和「商家自带的单」，差异化抽佣就无法落地。
2. **商家链接的落地下单**：大客集采链接和样品单的成交发生在买家侧。
3. **项目画像**：由商城上线备注和项目报备形成，是供应商愿意给项目价的前提。

| # | 商家侧诉求（会上） | 买家侧要提供的支持 | 落在哪一端 | 建议版本 |
| --- | --- | --- | --- | --- |
| S1 | 商家要看到品牌在政企渠道的曝光（商家价值的第一条） | 曝光、浏览、点击、加购、成交埋点，按商品 / 品牌汇总 | 会员端 + C 端商城 | V1.0 打底，V1.1 补全 |
| S2 | C 端「关注该商品」和浏览率 | C 端商品详情增加关注功能，计入行为数据 | C 端商城 | V1.1（消费商城改版） |

| S9 | 同类商品引入竞争、让价格竞争出来 | 同类 / 相似品并列展示与比价；搜索排序规则可配 | 会员端 + C 端商城 | V1.2 |
| S10 | 商家给服务商营销补贴 / 返佣，激励选品 | 会员选品时展示补贴标识；AI 选品与排序可参考补贴 | 会员端 | 随卖家侧版本 |

不需要买家侧支持的：ERP / 连接器接入、商家入驻与品牌审核、商家定价与佣金规则。这些由卖家侧独立规划。

需要和阿胜一起定的：订单来源枚举（S4）、链接与样品单的订单模型（S5、S6）、行为数据的汇总口径和脱敏粒度（S1、S3）。

### 项目归属与信息回传规则（11/3 确定）

- **客户归属按项目划分，不按客户划分**：
  - 集采项目：终端客户主要直接联系商家，算商家自带客户；
  - 采购项目：终端客户主要联系服务商，由服务商提供商城、福利发放、开票、售后等一系列企业采购服务，算服务商的客户。
- **回传给商家的项目信息只有四项**：客户类型、预算类型、预算金额、兑换订单的价格带（按商城实际订单计算）。终端客户名称和联系人不回传。
- **商家能看到具体服务商**：商家要知道订单是谁带来的，也要知道和谁议价。

对买家侧的影响：

1. **「项目」要成为会员端的正式对象**，而不只是商城备注。字段：项目类型（采购 / 集采）、客户类型、预算类型、预算金额、归属方（服务商或商家）。商城、询价单和订单都挂在项目下。
2. **价格带****由系统计****算**：按商城实际订单计算，服务商不填写。
3. **议价要留在平台内**：商家看得到服务商后，双方很容易转到线下。项目价申请和报价（S11）要做得比线下顺，成交才能归因。
4. **服务商知情**：服务商名称会展示给商家，需要在会员协议或项目创建时告知。

## 六、可行性判断

**11/20 前可以完成**：A1、A2、A4、B2、B3、C1、C2、D1、E3。做完这些，AI 选品可以在猫超、优品范围内做到「说条件 → 出结果」，结果与商品池规则一致。但做不到理解「科研院所 100 人发福利」这类开放式需求。

**主要风险**：

1. **人力**：2 人 × 1.5 个月的估算不含 AI 打标和评测，需要重新评估。
2. **京东**：负责人未定，接口文档过旧，影响跨源覆盖。
3. **标签质量**：AI 打标必须抽检，否则选品结果不可靠。
4. **实时性**：库存和价格不实时，AI 推荐后可能已无货，下单前需要二次校验。
