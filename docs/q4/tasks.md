# 采发发买家侧任务拆解（按版本）

2026-11-03 · @sanyuan

四个版本共 27 项任务。**圈定范围的唯一标准是该版本的产品目标**：不服务本版目标的，即使容易做也不纳入，列在文末「未纳入」。任务来源：11/2 会议、买家侧版本规划、商品库 AI 可调用任务拆解（A–E）、商家侧需买家侧支持事项（S1–S13）。

**优先级口径**：

- **P0**：没有它，本版目标不成立；必须随版上线。
- **P1**：明显提升目标达成；工时不足可顺延到下一版。
- **P2**：锦上添花；延期时优先砍掉。

任务的优先级是整体判断，子项可以低于任务本身。

### V2 规则细则：搜索、推荐与 AI 选品排序

**三条总原则：**

1. **只在当前商城已上架、有货的商品里找。** 商城是服务商的，搜索、推荐、AI 都不越过服务商的上架范围。
2. **服务商的设置优先于平台规则。** 服务商设的置顶（现有功能），平台规则不覆盖。
3. **V2 不加平台运营权重。**「平台核心供给」权重位预留但默认为 0；商家补贴标识和推荐权重随平台运营规则在 Q1 生效，生效后也只在同一相关性档位内起作用、不超过服务商置顶。

**一、搜索怎么找（召回）**

| 步骤 | 规则 |
| --- | --- |
| 范围 | 当前商城已上架、未下架、可售到员工收货地区的商品；员工没有收货地区时，按商城设置的默认三级地址查询可售 |
| 分词与纠错 | 中文分词；常见错别字纠正；同义词表由商品运营维护（如「衣架」=「晾衣架」） |
| 匹配字段 | 商品名称、品牌、类目、商品标签（V1-6 补充的标签） |
| 类目约束 | 搜索词能对应到一个类目时，只返回该类目及其下级类目的商品，避免「搜衣架出洗衣机」 |
| 无结果兜底 | 依次尝试：纠错和同义词后再搜 → 放宽到上级类目 → 仍无结果时展示无结果推荐位（V2-2.6），并记录无结果词 |

**二、搜索结果怎么排（默认综合排序）**

先按相关性分档，档内再按业务因子排；员工可以手动切换为按销量、价格升序或降序。

| 顺序 | 因子 | 说明 |
| --- | --- | --- |
| 1 | 相关性档位 | 名称完全命中 > 名称部分命中 > 品牌命中 > 类目命中 > 标签命中 |
| 2 | 服务商置顶 | 同一档内，服务商置顶的商品在前（现有置顶功能） |
| 3 | 本商城近 30 天销量 | 本商城员工买得多的在前 |
| 4 | 全平台近 30 天销量 | 新商城没有销量时用它补位 |
| 5 | 额度适配 | 单价不超过员工剩余额度的在前 |
| 6 | 上架时间 | 新上架的在前 |

**三、推荐位怎么出（V2 不做个性化）**

| 推荐位 | 出什么 |
| --- | --- |
| 首页 | 服务商配置的推荐商品优先；不足时补本商城近 30 天热销 |
| 详情页 | 同类目本商城热销，排除当前商品 |
| 购物车 | 价格不超过剩余额度、能把额度用满的商品，按本商城热销排 |
| 无结果页 | 本商城热销 + 额度内可兑换的商品 |

**四、AI 选品怎么排（V2-6）**

1. **理解需求**：识别额度（员工剩余额度，或对话里说的金额）、用途和对象（自用、送父母、给孩子等）、品类偏好、排除项（如「不要零食」）。
2. **硬过滤**：当前商城已上架且有货；单件或组合总价不超过额度；去掉排除项。
3. **排序**：
  1. 需求匹配度：品类、用途、标签命中越多越前（权重最高）
  2. 额度利用：组合总价在额度的 90%–100% 之间优先（允许混合付的商城为 90%–110%），少留零头
  3. 本商城销量，其次全平台销量；有好评率的参考好评率
  4. 服务商置顶的商品在同分时优先
  5. 多样性：同一品牌不超过 2 个，同一末级类目不超过 3 个
4. **输出**：5–8 个商品，或最多 3 套凑满额度的组合；每个附一句理由（命中什么需求、价格、销量）；可直接加购或兑换。
5. **边界**：不推无货商品；只显示商城售价，不显示成本价和接口价；理解不了或无结果时回退到搜索和分类（V2-6.6）。
6. **上线前评测**：用约 50 条常见问法（V2-6.8）测三个指标——推荐命中率、额度利用率、推荐采纳率。

**AI 选品业务规则**

| 规则 | 内容 |
| --- | --- |
| 两种推荐方式 | **AI 对话推荐**（耗 token）：员工说需求，按需求 + 余额推荐；**规则推荐**（不耗 token）：按余额 + 最近搜索或浏览的相似品推荐，用在搜索无结果页、购物车、AI 未开通或用量用完时 |
| 按余额推荐 | 默认以员工剩余额度为预算；对话里说了金额的以对话为准但不超过余额；商城不允许混合付时，单件或组合总价不超过余额，在余额的 90%–100% 优先；商城允许混合付时，选品范围放宽到余额的 90%–110%，超出部分由员工自付，推荐时标出需补差的金额；余额低于商城最低价商品时提示「额度已用完」，不再推荐（允许混合付的商城仍可推荐需补差的商品） |
| 按相似品推荐 | 相似 = 同末级类目 + 价格在参考商品 ±30% 以内 + 商品标签有重合；参考商品取最近一次搜索的结果或最近浏览的商品；排除已加购和已兑换的商品 |
| 范围 | 只在当前商城已上架、有货、可售到收货地区（或商城默认三级地址）的商品里推荐 |
| 开通方式 | 前期 token 由平台买单。服务商在项目视图里**按项目申请**，填发放人数和兑换期；运营在**运营管理后台审批**并设置预算；开通后该项目下所有商城的搜索结果页显示「AI 助手」入口（搜索功能保留不变），进入后提示「今日可对话 N 次」 |
| 用量管控 | 本期按对话次数管控，不做 token 计量。运营后台控制：项目级开关、项目总次数（发放人数 × 3）、每人每天 5 次、一次对话内追问 3 轮不另计；同一商城同样问法和同一档额度直接复用上次结果，不调模型、不计次；兑换期结束自动关闭；项目总次数用到 80% 提醒运营、可追加；员工当天或项目次数用完时不报错，自动切到规则推荐（「按你的余额，为你挑了这些」） |
| 用量可见 | 运营看全部项目的对话数、token 消耗、带来的兑换 GMV；服务商只看自己项目的对话数和带来的兑换，不能自行开启或加量 |
| 待定 | 审批标准（如发放人数、项目金额下限）、每人每日次数和单项目预算的默认值，由运营定 |

### V2 埋点规划：C 端全流程

**V2 的重点是 C 端体验和全流程埋点**：员工从进入商城到兑换、售后的每一步都要有数据，用来定位体验卡点、算版本门槛、核算 AI 对话次数。V1 新前端三个页面先接入（V1-7.5），V2 补全，V3 购物车和订单统一后补齐货源维度。

**规范**

- **命名**：对象_动作，小写加下划线，如 product_click。
- **公共字段**（每个事件都带）：事件时间、员工匿名编号、会话编号、商城编号、项目编号、服务商编号、当前页面、上一页面、终端（小程序 / H5 / PC）、新旧前端标记、灰度批次、收货地区（或商城默认三级地址）。

- **上报方式**：前端上报；兑换成功、售后等交易事件以服务端为准。
- **隐私**：不采集员工姓名、手机号；AI 对话文本脱敏后存。
