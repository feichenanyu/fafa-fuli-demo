采发发买家侧任务拆解（按版本）

最新通用 · 任务拆解最后更新 2026-11-03 17:21

2026-11-03 · @sanyuan

四个版本共 27 项任务。圈定范围的唯一标准是该版本的产品目标：不服务本版目标的，即使容易做也不纳入，列在文末「未纳入」。任务来源：11/2 会议、买家侧版本规划、商品库 AI 可调用任务拆解（A–E）、商家侧需买家侧支持事项（S1–S13）。

优先级口径：

  • P0：没有它，本版目标不成立；必须随版上线。
  • P1：明显提升目标达成；工时不足可顺延到下一版。
  • P2：锦上添花；延期时优先砍掉。

任务的优先级是整体判断，子项可以低于任务本身。

第一版 · 11/20 年货节存量增长版

目标：运营货盘线上化，服务商在管理商品的位置直接筛选、一键上架，聊完需求能自助询价、下单，以此做存量服务商的年货节营销增长；C 端商城购物车、分类、个人中心先迁移到新前端；项目信息补齐并按项目看经营，为项目闭环打底。

编号 任务 / 子项 优先级 业务价值
V1-1 场景货盘线上化（替代线下**表格乱飞）** P0 运营做好的货盘不再靠线下表格到处转发，服务商在系统里直接看到、筛选、上架**，带动存量 GMV**
V1-1.1 年货节二级场景配置，绑定规则商品池（多来源平台商品） P0 货盘按场景组好，服务商不用在全库里翻
V1-1.2 场景首页与场景商品页（会员价、市场价、市场价利润率；不露接口价） P0 服务商一眼看到能赚多少
V1-1.3 阿里权益会员的同品替换（平台猫超 / 优品按 SKU 换成自有货源） P0 自有货源会员也能直接用场景，存量交易不流失
V1-1.4 场景商品排序值、指定会员可见 P1 运营把主推商品放在前面
V1-1.5 货盘筛选：按品类、品牌、价格带、市场价利润率、货源、发货方式、商品标签筛选，可批量勾选 P0 服务商按客户需求挑货，不用翻整个货盘
V1-1.6 货盘准入标准：用商品池规则按近 28 天在架天数、发货方式、库存覆盖省份、近 28 天最低与平均到手价差筛出相对稳定的商品（阈值由运营定）；按预算档位组货；标出运营推荐；对服务商表述为「按稳定性筛选，供参考」，不承诺库存和货期 P0 货盘比服务商自己选品多出运营的判断：好卖、相对稳定、拿来就能提方案
V1-2 一键成交 P0 缩短从选货到成交的路径，春节档成交更快
V1-2.1 一键加购、购物车结算 P0 多商品一次下单
V1-2.2 一键代发：已有功能，兼容所有渠道来源的商品 P0 春节最常见的交易方式
V1-2.3 一键上架：已有功能，兼容所有渠道来源的商品；含加价规则（基于会员价/市场价/平均到手价统一按百分比调价） P0 服务商把货快速放进给甲方的商城
V1-2.4 一键询价：在场景货盘、搜索结果、商品详情里发起，生成集采询价单（不含报价单），询价时选择用在哪个商城（或「还没建商城」），数量、预算、交付时间、客户类型必填；V1 一个商城默认对应一个项目，项目报备上线后询价必填信息自动带入项目；「还没建商城」的询价单待关联，建商城时提示挂上；询价选商城不依赖报备，先做；集采价、活动价按项目询价，运营线下向供应商询价 P0 和客户聊完需求，服务商自己就能发起询价
V1-2.5 一键创建商城：已有功能，兼容所有渠道来源的商品（绑定场景模板和商品池） P2 工时不足时第一个顺延
V1-2.6 一键上架的定价策略（按规则自动调价）兼容所有渠道来源的商品；与加价规则是两套独立逻辑 P1 用定价策略的服务商上架多来源商品后，价格仍能自动调整
V1-2.7 统一收银：加购结算、一键代发统一从预付款账户扣款 P0 所有货源一个扣款口径，服务商不用分渠道付款、对账
V1-3 按项目看经营数据（并入项目视图） P****0 报备的项目信息真正用起来；一个甲方多个商城时，服务商不用自己汇总
V1-3.1 项目详情页展示该项目的订单数、交易额、利润和兑换价格带，复用现有订单、交易金额、利润口径；不在经营概览另加筛选，不新建看板 P0 兑现报备提示里说的用途，开发量最小
V1-4 项目关系与订单来源 P0 项目视图、后续商家数据和按来源结算都靠它；由系统自动建立，不靠服务商主动报备
V1-4.1 项目字段（不做独立报备入口，在项目视图里可补充编辑）：项目类型（采购 / 集采）、客户类型、预算类型、预算金额、归属方，记录报备时间；价格带不填写 P1 项目是闭环的主线；报备时间为后续归属规则留依据
V1-4.2 存量商城自动生成项目（无需服务商确认）：一个商城默认生成一个项目，项目名用商城名称，同一甲方多个商城由服务商后续合并；系统预填（客户类型推断），服务商可在项目视图里修改 P0 存量商城是大头，几乎不费事就能补齐
V1-4.3 价格带按商城实际订单自动计算（历史商城按已有订单计算），算出后在项目详情页展示；商家侧是否展示随 V4 数据对接再定 P1 数据真实，服务商不用填
V1-4.4 项目信息在询价时顺手带上：询价必填的客户类型、预算写入所选商城对应的项目；其他填写项均为选项 P0 不单独填表，顺手完成
V1-4.5 报备提示：项目信息将用于经营管理数据统计，本版不提供给任何第三方；已报备项目的集采询价优先跟进，后续项目供货价申请资格以报备时间为准；不承诺保护；V4 起只回传客户类型、预算类型、预算金额、兑换价格带和服务商名称，不回传客户名称和联系人 P1 讲清填了有什么用，打消服务商顾虑
V1-4.6 商城、询价单、订单挂到项目下 P0 订单能说清属于哪个项目
V1-4.7 订单来源枚举（搜索 / 场景 / AI 选品 / 推荐 / 商家链接 / 样品单）与货源类型 P0 后续差异化佣金和货源口径的依据
V1-4.8 未关联项目的商城和订单提示，一键去报备 P2 把没报备的项目引导回来
V1-5 工作台轻量调整：新增项目视图 P****0 存量会员一进来就看到年货节；项目、商城、询价单、订单在一处看到，从项目直接发起动作
V1-5.1 年货节场景置顶 P0 把流量引到年货节
V1-5.2 新增项目入口 P0 V1-4 的入口，没有就建不了项目
V1-5.4 项目列表：每个项目一行，显示商城数、询价中的单数、交易额、利润；未关联项目的商城和询价单单独提示 P0 服务商按甲方项目看全局，不用在几个菜单间来回切
V1-5.5 项目详情：一页聚合该项目的商城、询价单、订单和经营数据（含 V1-3.1），只聚合已有数据，不新增业务逻辑 P0 「按项目看账」有具体的地方，服务商感受到报备的好处
V1-5.6 从项目发起动作：建商城、去货盘选品上架、发起询价，自动带上项目信息 P0 动作从项目出发，项目信息自然补齐；V3 完整重构在此基础上扩展
V1-5.3 下线名片、企微等无人使用的栏目 P2 界面更清爽，不影响成交
V1-6 商品池运营：渠道商品字段补充与标签化 P0 商品运营把猫超、京东商品缺的信息补上，变成标签供商品池规则自动组货；渠道字段不全不再卡住年货节选品
V1-6.1 按渠道（猫超、京东）清单导入补充字段，按 SKU 匹配，可不定期重复导入 P0 商品运营不用逐个改，批量补齐
V1-6.2 补充字段转为商品标签或营销标签，并作为商品池选品规则的条件 P0 规则能按「年货节」「送礼」等标签自动组货
V1-6.3 人工补充字段不被渠道同步覆盖，并明确两者冲突时以哪个为准 P0 运营补的信息不白补
V1-6.4 标签管理：区分商品标签与营销标签，支持增删改；营销标签可设有效期 P1 档期结束后营销标签自动失效，商品池不乱
V1-6.5 导入结果校验与失败明细 P1 运营知道哪些没补上
V1-6.6 渠道可扩展：新渠道按同一导入模板接入 P1 后续接入其他渠道不用重做
V1-6.7 长期未更新字段和过期标签提醒 P2 提醒运营不定期维护
V1-7 C 端商城新前端（前后端分离，首批：购物车、分类、个人中心） P0 **C 端改版的技术底座；**先迁购物车、分类、个人中心，为第二版的 AI 选品和统一展示铺路
V1-7.1 购物车、分类、个人中心迁移到新前端（独立工程与接口层） P0 新体验的前提
V1-7.2 迁移页面涉及的旧配置与数据兼容 P0 存量商城换前端后不丢内容
V1-7.3 按站点灰度上线，三部分可回退旧前端（技术上线方案，不做用户可见的新旧切换） P0 春节兑换高峰前不出事故
V1-7.4 新旧前端之间登录态和页面跳转无缝（如旧详情页加购后进入新购物车） P0 员工感知不到两套前端
V1-7.5 新前端接入统一埋点框架：购物车、分类、个人中心的页面浏览、分类点击、商品曝光与点击、加购、购物车操作、去结算，带新旧前端标记 P0 灰度期间能对比新旧前端；V2 全流程埋点在此基础上扩展
V1-8 运营兜底：待补录项目清单 P1 交易额大头的项目信息由运营补齐，不全靠服务商
V1-8.1 新运营后台列出有交易、未报备的商城，按交易额排序 P1 运营先补头部
V1-8.2 运营代服务商补录项目信息，标记来源为运营 P1 补录可追溯
V1-9 货盘入口进到服务商管理商品的地方 P0 服务商在平时管货的位置直接取用运营货盘，不用再手动导入或找客户运营帮忙

V1-9.3 自助搜索：现有找货搜索覆盖可见的场景货盘，结果可直接询价、加购下单、上架 P0 和客户聊完需求，自己搜、自己询价下单
V1-9.4 新运营后台记录每个货盘被上架的商城数、商品数和询价数；线下表格转发和手动导入停用 P1 运营知道货盘有没有被用起来，客户运营不再代导入
V1-10 项目数据权限与脱敏 P0 把「不用服务商客户数据绕开服务商」写进系统；项目视图上线后运营后台就能看到项目明细，必须同版上线
V1-10.1 不存终端企业联系人和联系方式字段；平台消息和通知只发给服务商账号 P0 没有数据就无法触达，最强的约束
V1-10.2 项目明细权限：服务商只看自己的项目；运营后台默认只看汇总，查看单个项目明细需要特定角色权限 P0 看得到明细的人越少越安全
V1-10.3 客户名称加密存储，运营后台显示脱敏名称（如「某央企国企·北京」）；含客户名称的明细不支持导出 P0 运营做业务分析够用，又拿不到具体客户
V1-10.4 访问留痕：运营查看、导出项目明细记录日志（谁、何时、哪个项目），定期抽查 P1 出了问题查得到人，也有威慑作用
V1-10.5 页面水印：运营后台涉及项目和客户信息的页面加明水印（查看人账号 + 时间），允许导出的汇总文件同样带水印 P1 截图或文件外传能追到人，降低线下外泄

运营配合（不占研发）：关联了项目的集采询价单，运营优先跟进并拿项目信息帮服务商争取更好的价格；年货节选品建议、货盘调整和活动资源优先给已报备项目的商城。

目标：让员工在项目商城里顺利完成兑换，赶在 1 月兑换高峰前上线；C 端 AI 选品与统一商品展示随本版上线；全流程埋点上线，定位体验卡点；购物车、订单、售后统一移到 V3，商品库切换后一起改。

编号 任务 / 子项 优先级 业务价值
V2-1 统一商品展示 P0 全渠道商品在商城里展示一致，商城显得专业；也是 AI 推荐结果的展示载体
V2-1.1 全货源统一商品卡与详情模板 P0 不同货源不再五花八门
V2-1.2 关键样式对标天猫超市并固定，不开放站点自定义 P0 避免站点配乱
V2-2 找得到 P0 员工找到想要的商品，兑换转化率提升
V2-2.1 搜索修正（分词、无结果兜底） P0 解决「搜衣架出洗衣机」
V2-2.2 规则排序（相关性、销量、价格） P1 好卖、相关的商品在前面

V2-2.4 排序中预留「平台核心供给」权重位 P2 为后续平台运营规则留口子

V2-3 看得懂（补充） P****2 补充信息让员工选得更有依据，商家品牌有曝光（统一商品展示**见 V2-1）**
V2-3.3 评价 / 好评率（京东）、热度展示 P2 员工选择更有依据

V2-5 全流程埋点 P0 员工从进入商城到兑换、售后每一步都有数据，能定位体验卡点；商家拿到分层数据

V2 规则细则：搜索、推荐与 AI 选品排序

三条总原则：

  1. 只在当前商城已上架、有货的商品里找。 商城是服务商的，搜索、推荐、AI 都不越过服务商的上架范围。
  2. 服务商的设置优先于平台规则。 服务商设的置顶（现有功能），平台规则不覆盖。
  3. V2 不加平台运营权重。「平台核心供给」权重位预留但默认为 0；商家补贴标识和推荐权重随平台运营规则在 Q1 生效，生效后也只在同一相关性档位内起作用、不超过服务商置顶。

一、搜索怎么找（召回）

步骤 规则
范围 当前商城已上架、未下架、可售到员工收货地区的商品；员工没有收货地区时，按商城设置的默认三级地址查询可售
分词与纠错 中文分词；常见错别字纠正；同义词表由商品运营维护（如「衣架」=「晾衣架」）
匹配字段 商品名称、品牌、类目、商品标签（V1-6 补充的标签）
类目约束 搜索词能对应到一个类目时，只返回该类目及其下级类目的商品，避免「搜衣架出洗衣机」
无结果兜底 依次尝试：纠错和同义词后再搜 → 放宽到上级类目 → 仍无结果时展示无结果推荐位（V2-2.6），并记录无结果词

二、搜索结果怎么排（默认综合排序）

先按相关性分档，档内再按业务因子排；员工可以手动切换为按销量、价格升序或降序。

顺序 因子 说明
1 相关性档位 名称完全命中 > 名称部分命中 > 品牌命中 > 类目命中 > 标签命中

5 额度适配 单价不超过员工剩余额度的在前

三、推荐位怎么出（V2 不做个性化）

推荐位 出什么
首页 服务商配置的推荐商品优先；不足时补本商城近 30 天热销
详情页 同类目本商城热销，排除当前商品
购物车 价格不超过剩余额度、能把额度用满的商品，按本商城热销排
无结果页 本商城热销 + 额度内可兑换的商品

四、AI 选品怎么排（V2-6）

  1. 理解需求：识别额度（员工剩余额度，或对话里说的金额）、用途和对象（自用、送父母、给孩子等）、品类偏好、排除项（如「不要零食」）。
  2. 硬过滤：当前商城已上架且有货；单件或组合总价不超过额度；去掉排除项。
  3. 排序：
  4. 需求匹配度：品类、用途、标签命中越多越前（权重最高）
  5. 额度利用：组合总价在额度的 90%–100% 之间优先（允许混合付的商城为 90%–110%），少留零头
  6. 本商城销量，其次全平台销量；有好评率的参考好评率
  7. 服务商置顶的商品在同分时优先
  8. 多样性：同一品牌不超过 2 个，同一末级类目不超过 3 个
  9. 输出：5–8 个商品，或最多 3 套凑满额度的组合；每个附一句理由（命中什么需求、价格、销量）；可直接加购或兑换。
  10. 边界：不推无货商品；只显示商城售价，不显示成本价和接口价；理解不了或无结果时回退到搜索和分类（V2-6.6）。
  11. 上线前评测：用约 50 条常见问法（V2-6.8）测三个指标——推荐命中率、额度利用率、推荐采纳率。

AI 选品业务规则

规则 内容
两种推荐方式 AI 对话推荐（耗 token）：员工说需求，按需求 + 余额推荐；规则推荐（不耗 token）：按余额 + 最近搜索或浏览的相似品推荐，用在搜索无结果页、购物车、AI 未开通或用量用完时
按余额推荐 默认以员工剩余额度为预算；对话里说了金额的以对话为准但不超过余额；商城不允许混合付时，单件或组合总价不超过余额，在余额的 90%–100% 优先；商城允许混合付时，选品范围放宽到余额的 90%–110%，超出部分由员工自付，推荐时标出需补差的金额；余额低于商城最低价商品时提示「额度已用完」，不再推荐（允许混合付的商城仍可推荐需补差的商品）
按相似品推荐 相似 = 同末级类目 + 价格在参考商品 ±30% 以内 + 商品标签有重合；参考商品取最近一次搜索的结果或最近浏览的商品；排除已加购和已兑换的商品
范围 只在当前商城已上架、有货、可售到收货地区（或商城默认三级地址）的商品里推荐
开通方式 前期 token 由平台买单。服务商在项目视图里按项目申请，填发放人数和兑换期；运营在运营管理后台审批并设置预算；开通后该项目下所有商城的搜索结果页显示「AI 助手」入口（搜索功能保留不变），进入后提示「今日可对话 N 次」
用量管控 本期按对话次数管控，不做 token 计量。运营后台控制：项目级开关、项目总次数（发放人数 × 3）、每人每天 5 次、一次对话内追问 3 轮不另计；同一商城同样问法和同一档额度直接复用上次结果，不调模型、不计次；兑换期结束自动关闭；项目总次数用到 80% 提醒运营、可追加；员工当天或项目次数用完时不报错，自动切到规则推荐（「按你的余额，为你挑了这些」）
用量可见 运营看全部项目的对话数、token 消耗、带来的兑换 GMV；服务商只看自己项目的对话数和带来的兑换，不能自行开启或加量
待定 审批标准（如发放人数、项目金额下限）、每人每日次数和单项目预算的默认值，由运营定

规范

  • 命名：对象_动作，小写加下划线，如 product_click。
  • 公共字段（每个事件都带）：事件时间、员工匿名编号、会话编号、商城编号、项目编号、服务商编号、当前页面、上一页面、终端（小程序 / H5 / PC）、新旧前端标记、灰度批次、收货地区（或商城默认三级地址）。

  • 上报方式：前端上报；兑换成功、售后等交易事件以服务端为准。
  • 隐私：不采集员工姓名、手机号；AI 对话文本脱敏后存。
