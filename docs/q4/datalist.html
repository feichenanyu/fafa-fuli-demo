一、为什么现在就要准备

买家侧要在 V1 把字段、口径和埋点定下来，让每一笔订单从一开始就带着项目、来源和货源信息。 原因是卖家侧会用这些数据做三件事，而订单来源和埋点没法事后补：

  • 按订单来源结算佣金：区分商家自带客户和服务商客户。
  • 商家拿项目数据给项目供货价：看项目四项，以及商品在项目里的表现。
  • 平台商家商品进入选品后看效果：展示、点击、成交分层统计。

三条原则：

  1. 先定口径，再攒数据，最后才做展示。 页面可以晚做，字段和埋点不能晚。
  2. 服务商的客户只做汇总，不暴露单个企业。 一旦服务商觉得平台在绕开他，报备就推不动了。
  3. C 端员工只做汇总，不做个人画像。 给商家的只有汇总数据。

二、买卖双方数据约定（先和卖家侧对齐）

五项约定要在 V1 开发前和卖家侧定下来，它们是两边接口和结算的依据。

约定项 要定什么 用在哪 要求时间
订单来源 取值：搜索 / 场景 / AI 选品 / 推荐 / 商家链接 / 样品单（后两项先预留）；归因规则：一笔订单经过多个入口时算哪个（建议按加购时的入口） 卖家侧按来源结算佣金 V1 上线前
货源类型 平台商家 / 服务商自有供应商 / 自有猫超优品 / 平台猫超京东 结算口径；服务商货盘构成；V3 迁移指标 V1 上线前
项目四项 客户类型、预算类型的取值两边用同一套；价格带分段规则 商家看项目、给项目价 V1 上线前
回传范围 回传哪些字段、什么时候回传、商家哪些角色能看；只有四项加服务商名称，不含客户名称和联系人 V4 项目数据回传 V3 前
商品编号对应 买家侧商品和卖家侧新商品库的编号怎么对上 商品表现数据、平台商家选品 12 月商品库清洗时

三、六类数据准备清单

订单来源和货源类型最急，其次是项目信息和 C 端埋点框架。 服务商画像和终端企业画像不用新收集，用前三类数据算出来。

数据 卖家侧 / 平台拿来做什么 买家侧要准备的 来源 落在哪版 边界
1. 订单来源与货源类型 按来源结算佣金；区分商家自带客户 每笔订单下单时写入来源和货源类型；按第二节的归因规则实现 系统自动 V1-4.7 最急：历史订单没法补
2. 项目信息 商家看项目四项，决定给不给项目价 定清「一个项目」怎么算（建议：一个甲方的一次预算）；价格带按实际订单计算 服务商报备（见第五节） V1-4 客户名称选填；只回传四项 + 服务商名称
3. 服务商画像 商家知道订单是谁带来的；平台挑 V3 迁移对象、做会员运营分层 货盘构成（各类货源占比）、甲方数、项目数、商城数、GMV、常用品类、价格带、活跃度 从 1、2 和现有交易算 现在先做一次存量分析 只给平台内部用；商家只看到服务商名称
4. 终端企业画像 商家看不同客户类型买什么；场景运营按客户类型组货 客户类型、行业、规模、预算类型和金额按类型汇总 从 2 算 V1-4 起积累 只做汇总，不对外暴露单个企业
5. C 端员工行为 商品分层数据；额度用了多少；不同客户类型偏好哪些品类 统一埋点规范；建议在 V1 新前端上线时就带上埋点框架 埋点 V1-7 打底，V2-5 补全 新前端要有隐私政策；只给汇总
6. 商品在项目里的表现 商家定项目价的依据 曝光按商城、按项目统计；平台商家商品有唯一编号 从 1、2、5 算 V2-5、V4-2.3 依赖卖家侧 12 月商品库清洗

四、不做画像页面，数据怎么积累

画像不是一个页面，而是一组定期计算、放在数据中台里的标签表。 先让数据在业务里被用起来，等有人需要看时再做展示。

四层积累：

  1. 业务字段写进交易：项目、来源、货源类型在建商城、上架、下单时就写入订单和商城，不另记一份。
  2. 行为埋点：C 端展示、点击、加购、成交、搜索词（含无结果词）、AI 选品对话。
  3. 标签表定期计算：数据中台按周或按月跑出三张表——服务商标签表、终端企业按类型汇总表、商品 × 项目表现表。
  4. 按月存快照：每月底把标签存一份，保留变化轨迹。比如某个 B 类服务商自有货占比从 90% 降到 60%，就是 V3 迁移有效的证据。

不做页面，数据用在这些地方：

谁用 怎么用 已有载体
会员运营 在新运营后台的会员列表里按标签筛选，比如「自有货占比高、GMV 前 20」 列表增加筛选字段，不新建页面
卖家侧招商 头部 B 类服务商自有供应商清单，作为 V3 推动入驻的目标名单 导出表
商家 项目四项、商品在项目里的表现 V4 回传接口
服务商 按项目看总账 V1-3 现有经营概览加项目维度
产品和管理层 版本门槛、月度复盘 BI 报表或 SQL 查询

每月检查一次数据质量：订单来源完整率、项目报备覆盖率（按 GMV）、埋点覆盖率。三项中任何一项低于门槛，先修数据，再谈画像。

五、让服务商心甘情愿补项目信息

V1 不承诺保护，只给当场能兑现的好处；保护在 V4 随项目供货价一起落地。 V1 的询价由平台运营线下向供应商询价，项目信息不会到商家手上，不存在商家绕开服务商的问题；大家都用基础供货价，平台也没有排他的东西可以拿来保护。

版本 服务商得到什么 怎么兑现
V1 报完就能按项目看账 经营概览里立刻出现这个项目的订单、交易额、利润（V1-3）
V1 集采询价优先跟进 已报备项目的询价单，运营优先线下向供应商询价
V4 项目供货价资格与排他 同一甲方、同一预算周期，只有先报备的服务商能申请项目价；商家不能对同一项目给第二家项目价，也不能在平台内绕开他直接报价
V4 撞单时以报备时间为准 规则 V1 先公布，V4 生效

V1 报备提示（只说用途和好处，不说保护）：「项目信息仅用于你的经营数据统计，本版不提供给任何第三方；已报备项目的集采询价将优先跟进；后续项目供货价的申请资格以报备时间为准。」

同时把填写成本压到最低：

  • 存量商城由系统自动生成项目，无需服务商确认（V1-4.2）。
  • 项目信息在询价时顺手带上，也可在项目视图里补充，不做独立报备入口（V1-4.4）。
  • 价格带不用填，按订单自动算（V1-4.3）。
  • 客户名称选填。

运营补录的定位是兜底：只补交易额靠前、但服务商还没确认的商城；补录后仍由服务商确认。

V1 门槛看****信息补全占比：商城已自动生成项目，覆盖率接近 100%，改看「带客户类型和预算的项目占比」，即通过询价或编辑补全信息的项目有多少。预算金额、客户类型填得准不准，放到 V4 和项目价一起解决——那时报备和钱挂钩，服务商才有动力认真填。

六、需要用户主动发起的数据

最有价值的主动数据是「需求」：服务商的询价和项目价申请、员工的搜索词和 AI 对话。 它们告诉商家和平台「缺什么货、什么价」，而且都是用户在办自己的事时顺手产生的。终端企业本轮不直接入驻，它的数据经服务商间接产生。

发起人 数据 他为什么愿意发起 卖家侧 / 平台用途 状态
服务商 项目报备 按项目看账、询价优先跟进 项目四项、终端企业汇总 已排 V1-4
服务商 集采询价单（品类、数量、预算） 大单要更好的价 商家看到真实的大单需求；平台知道缺什么货 已排 V1-2.4
服务商 项目价申请 拿到更低成本 商家谈价的依据；谈成率、谈定价差 已排 V4-1
服务商 商城 AI 选品开关 自己控制给甲方的商城 哪些商城开了 AI，用来分析效果 已排 V2-6.4
服务商 找不到货的求购（品名、价位、数量） 平台帮他找货 给卖家侧招商的缺货清单 建议新增，可先用询价单承接
终端企业（经服务商） 发放额度、发放人数、兑换期 服务商配置商城时本来就要填 人均额度、额度使用率；项目预算校验 待确认现有商城是否已有这些字段
C 端员工 搜索词（含无结果词） 想找到要的东西 最直接的缺货信号 已排 V2-2，需要确认无结果词入库
C 端员工 AI 选品对话（预算、用途、偏好） 快速花完额度 自然语言的需求数据 已排 V2-6；存储前脱敏
C 端员工 关注商品、售后原因 留着以后换、解决问题 商家的兴趣和质量数据 V2-5.3（P2）、V2-4.3

不建议本轮做面向甲方的数据收集（如满意度问卷）：甲方是服务商的客户，平台直接触达会触及服务商的顾虑。

七、11 月行动与待确认

11 月先做五件事：

  • 和卖家侧定下第二节的买卖双方数据约定（至少前三项）
  • 和数据中台定三张标签表的字段和计算频率，以及月度快照
  • 做一次服务商存量分析：验证 B、C 类为主的判断，拉出头部 B 类自有供应商 GMV 清单
  • V1 新前端（购物车、分类、个人中心）上线时带上统一埋点框架和隐私政策
  • 按新口径改报备提示：只说信息用途和询价优先，不承诺保护；公布项目价资格以报备时间为准

待确认：

  1. V4 项目价排他的「同一项目」边界：同一甲方换预算周期或预算类型（如年货节和中秋）是否算新项目；同一甲方同时出现集采项目和采购项目时怎么归属。
  2. 订单来源归因规则（建议：按加购时的入口）。
  3. 现有商城是否已记录发放额度、发放人数、兑换期。
  4. 「找不到货的求购」是否新增，还是先用询价单承接。

八、各类数据详细字段

8.5 C 端员工行为（按事件记录，匿名）

九、终端企业数据：收集思路与用途

核心思路：不额外要、不绕开服务商、只用汇总。 终端企业是服务商的客户，本轮平台不直接接触它。数据只从两个地方来：服务商在办自己的事（询价、建商城、配置商城）时顺手留下的，和商城运转自然产生的。单个企业的数据只给它所属的服务商看，平台和商家只用汇总。

9.1 能收集什么

来源 数据 服务商要不要额外做事
服务商询价或在项目视图里填的 客户类型、行业、规模区间、所在省市、预算类型、预算金额、发放人数、兑换期、客户名称（选填，不外传） 不用：询价本来就要填，其余选填
商城配置自带的 默认三级地址（推出所在地区）、是否允许混合付、额度发放方式、开商城时间、AI 助手是否开通 不用
交易产生的 兑换 GMV、品类和品牌结构、兑换价格带、货源结构、额度使用率、未兑换余额、兑换高峰日、售后率与原因 不用
员工行为汇总 登录率（登录人数 ÷ 发放人数）、人均兑换金额、搜索热词和无结果词、AI 提问里的需求（脱敏） 不用
时间维度 采购时点（年货节 / 端午 / 中秋 / 生日等）、下一预算期是否再开项目（续约） 不用

不收集：终端企业的联系人和联系方式；员工个人信息和个人画像。

9.2 用在哪里

谁用 用来做什么 看到的粒度 版本
服务商 在项目详情里看自己甲方的兑换情况、员工偏好、未兑换余额，用来复盘、谈续约、做下次方案——这也是服务商愿意补信息的理由 自己的单个项目 V1 起（项目视图）
场景运营 按客户类型 × 预算类型组货盘；按人均额度分布定预算档位；按采购时点提前准备下一档期货盘 汇总 V1 起
商品运营与卖家侧招商 搜索无结果词、AI 提问里的缺货需求 → 缺货清单 汇总 V2 起
AI 助手 同类客户的热门商品作为新商城的推荐参考 汇总 V2 起
商家 客户类型、预算类型、预算金额、兑换价格带，以及同类客户的品类偏好，用来给项目价、做营销 单项目只给这五项；偏好只给汇总（一个组合至少 5 个项目） V4
会员运营 发现续约窗口（兑换期快结束、额度使用率高的项目），提醒服务商提前跟甲方谈下一期 只通过服务商 V2 起
明年终端企业入驻 了解哪类企业、多大预算适合自助采购，用于设计入驻方案 只用汇总，不用单个企业名单 明年

9.3 红线写进系统规则

红线不靠口头约定，靠六层系统限制（任务见 V1-10、V4-2.4）。 平台和商家都不用这些数据直接触达终端企业。

限制 规则 版本
1. 不存触达信息 系统里没有终端企业联系人和联系方式字段；平台消息和通知只能发给服务商账号。没有数据就无法触达，这是最强的约束 V1
2. 明细只给所属服务商 单个项目的明细只有所属服务商的账号能看；运营后台默认只看汇总，查看单个项目明细需要特定角色权限 V1
3. 敏感字段脱敏 客户名称加密存储，运营后台显示为脱敏名称（如「某央企国企·北京」）；含客户名称的明细不支持导出 V1
4. 商家接口白名单 商家侧只开放五个字段和汇总接口；汇总接口不足 5 个项目的组合不返回，地区只到省、金额只给区间，不支持按服务商或企业筛选，防止反推 V4
5. 访问留痕 运营查看或导出项目明细、商家调用接口都记录日志，定期抽查 V1 记录，V4 覆盖商家接口
6. 页面水印 运营后台涉及项目和客户信息的页面加明水印（查看人账号 + 时间），允许导出的汇总文件同样带水印；截图或文件外传能追到人 V1

系统限制不了的：有权限的人看到信息后在线下使用。这部分靠权限最小化、访问留痕，再加会员协议和商家协议里的数据使用条款来约束（V4-2.2 服务商知情告知一并写明）。

十、订单流失数据

流失分三层看：C 端员工、服务商、平台。 目的是知道订单丢在哪、为什么丢，让服务商能换货补货，让平台能谈价、招商。报表任务见 V2-5.11。

层 流失点 要记录的字段 谁用 版本

十一、福利采购行业数据

这几类数据是福利采购行业特有的，甲方、服务商和平台都会用到。 大多数能从现有业务里取，不用服务商额外填。

类别 数据 用在哪 来源
发放与过期 发放方式（积分 / 卡券 / 额度）、人均标准、有效期、过期作废率 服务商给甲方汇报「钱有没有发到员工手上」；平台定预算档位 商城配置、卡券、订单
合规 品类合规标签（购物卡、烟酒等禁限品）、各地工会福利标准（如春节人均限额） AI 选品和标案分析不推荐不合规商品；货盘准入 商品运营打标；工会标准由运营整理
履约质量 按货源和供应商统计发货时效、签收率、破损率、售后时效 供应商评分、货盘准入、选品排序 订单与物流
卡券 核销率、核销时间分布、未核销金额 服务商给甲方汇报；卡券选品 卡券模块
价格波动 猫超、京东到手价的变化、市场价变化 货盘稳定性筛选（V1-1.6）、高利润提示（V3-8.2） 商品池字段补充、渠道同步
开票与对账 开票类型、开票时长、对账差异笔数和金额 解决服务商对账开票痛点的依据 财务模块
